skill 记录一套可复用的做法：怎么完成一件事。它管「怎么做」，和「什么时候做」分开。官方建议：先把任务做成一次性任务并跑稳，再存成 skill，最后才做成 routine。

## 1. 什么时候该存

满足下面几条再存，比一上来就「做成自动化」省用量：

- 你已经亲手跑过至少一轮，结果可接受。
- 步骤、判断标准和交付格式已经说得清。
- 需要人点头的动作（外发、付款、删数据、改生产）已经标成审批点。
- 你预计未来还会重复做，或要交给另一个 Bot / 例程调用。

还在试探时，先把做法写在对话或 `/workspace` 笔记里；稳定后再归档成技能。过早固化会把半成品步骤锁进例程。

## 2. 一条好技能写清六件事

官方列出的六项，写成检查清单：

1. **什么时候用**：触发场景与不适用场景。
2. **需要哪些输入和权限**：连接器、文件路径、登录。
3. **工作的顺序**：先读什么、再写什么、失败怎么停。
4. **怎么验证结果**：格式、条数、链接是否齐全。
5. **交付什么**：对话摘要、文件路径、草稿卡。
6. **什么需要审批**：外发、购买、删除、发布、生产变更。

**描述（名称与适用说明）特别重要**：以后你在 `/` 菜单里扫一眼就要知道该不该调用它。名称要具体（「每周账号体检」优于「处理一下」）；适用 / 不适用各写一两句，避免例程在错误场景触发。

::: example 存一个技能
```text
把刚才这套流程存成一个技能，叫「每周账号体检」。
写明数据来源、风险判定标准、输出格式，以及「联系客户必须先得到我的批准」这条规则。
```
:::

::: example 写得不够的技能（反例）
```text
帮我处理一下客户相关的事。
```
:::

反例缺场景、缺输入、缺验证、缺审批边界。例程若直接调用这种技能，要么空转，要么越权。

## 3. 你的私有技能 vs 插件自带技能

在 **Connect apps** 里既能发现应用插件，也能看到打包好的技能。装好的插件可能附带官方或服务商提供的用法说明；**你自己存下来的**则落在 **Private skills**——这是一份账号级共享库，所有 Bot 都能看见，但某个 Bot 可能还需要对应的连接器或登录才能真正跑通。

不要把「私有技能」理解成「每个 Bot 各有一份互不相通的副本」。改一处，所有会调用它的 Bot / 例程都会受影响——所以改完要重新 **Test run** 依赖它的例程。

桌面输入框输入 `/` 引用已保存的技能；用 `@` 提及 Bot、群、例程和连接器。

![Grok Bot 应用与技能面板搜索、分类标签与添加/连接](/tutorial/skills-panel.png)

侧边栏 **Connect apps** 打开后可搜应用与技能；**已连接** 入口与分类标签在上方，列表项旁是 **添加** 或 **连接**。

技能没出现在 `/` 菜单里时，打开 **Connect apps → Your plugins → Manage plugins and skills**，确认它列在 **Private skills** 下。

## 4. Teach a task：直接演示一遍

当 **Teach a task** 可用时，你可以演示一次浏览器流程，让 Bot 记下来：

1. 打开与单个 Bot 的对话和它的电脑视图。
2. 选 **Teach a task**。
3. 说明你要演示的结果。
4. 完整做一遍。
5. 停止录制，检查 Bot 生成的技能。
6. 先在安全的例子上测试，再安排时间或例程。

录制最长十分钟，不录麦克风。演示时不要暴露密钥，凭证走安全交接。生成的技能只是草稿：一次示范里看不出来的判断规则、失败处理和审批边界，需要你自己补上。

控件若暂时看不到，属于逐步开放。那时改用文字说明 + 已完成任务，请 Bot 整理成技能即可。Teach a task 仅桌面端提供，手机端不能录。

## 5. 改技能与退役

流程变了（网站改版、连接器字段变了、审批规则变了）就重跑一次手动任务，再让 Bot 更新技能说明。不再使用的技能从库里删掉或改名标「停用」，避免例程引用到过期步骤。

**不要把账号专属 ID 写死进可分享的技能**：数据库 ID、内部频道名、客户标识、webhook 地址等，应写成「由调用方提供」或放在本机 `/workspace` 配置文件里。技能若会被复制到模板或分享给别人，先剥掉密钥与内部地址（见[共建](/contribute/)）。

## 6. 从一次成功任务到技能的对话模板

跑通之后，可以直接丢给 Bot：

::: example 归档模板
```text
请把刚才成功的流程存成技能，名称：[名称]。
适用：我在什么情况下应该调用它。
不适用：哪些情况应拒绝或改问我。
输入：需要我提供哪些链接、文件、账号或时间范围。
步骤：按顺序列出；每一步注明用连接器还是浏览器。
验证：怎样算合格（字段、条数、链接、截图位置）。
交付：回我什么格式、放在哪个路径或哪个库。
审批：哪些动作必须停牌；缺数据时是报错还是跳过。
```
:::

## 7. 和用量的关系

社区里常见「一周额度很快见底」的讨论，官方与员工回复强调：工具调用、浏览器、子代理和反复重读长对话都会计入工作量。技能写清楚、减少无效重试、一事一对话，通常比「把所有步骤塞进一个超级技能」更省。详见[新手坑点](/faq/pitfalls/)。本站不写具体额度数字。

## 8. 和例程怎么配合

技能写好后，再在[例程](/workbench/routines/)里决定「何时跑、由哪个 Bot 跑」。例程说明应写**意图与验收**，而不是把某次成功时的工具调用序列冻成死菜谱——源系统一变，死菜谱就会碎。可对照场景[每日 AI 情报例程](/scenarios/intel-digest/)与[Test run 过了才响的晨报](/scenarios/tested-briefing/)。

## 你要检查什么

- 六要素是否齐全，尤其是「验证」和「审批」。
- `/` 菜单里能否点到它；缺的话是否落在 **Private skills**。
- Teach 草稿是否补了失败分支与审批。
- 是否先 Test / 手动验证，再绑到例程。
- 可分享技能里是否残留账号专属 ID 或密钥。

## 常见坑

- 没跑通就存技能，再绑例程，天天空转。
- 名称含糊，半年后不知道该不该调用。
- 把内部频道 ID 写死进技能后拿去分享。
- Teach 完不补审批边界，录制里「顺手点了发送」。
- 改了技能却不重跑依赖它的例程 Test run。
