routine 决定某个流程什么时候跑、由哪个 Bot 跑。官方给的例子：工作日早上八点跑一遍客户风险技能；Slack 频道里出现工单链接时去复现问题。Skill 管「怎么做」，Routine 管「何时做」——先技能后例程。

## 1. 定时例程（cron 式）

向将要拥有这条例程的 Bot 发一句话即可创建。确认这六项再启用：

1. 归属哪个 Bot 
2. 时间表与时区 
3. 输入来源 
4. 预期结果 
5. 审批边界 
6. 数据源缺失时怎么办（不要静默用旧数据）

后台例程在你合上笔记本后依然运行。时间表至少间隔五分钟。

新手默认：优先选**工作日白天**时段（例如工作日早上），方便你看着第一次正式跑；半夜高频闹钟更容易在无人值守时撞上过期审批卡（约十分钟过期，见[安全与审批](/workbench/security/)）。

::: example 官方风格的定时说明
```text
每个工作日早上 8:00，对当前客户名单跑一遍「每日客户风险」技能。
在本对话贴一份带链接的观察名单。不要联系客户。
若源数据不可用，报告失败，不要用旧数据凑数。
```
:::

## 2. 事件触发（listener 式）

Cursor 账号集成可以在事件发生时启动例程，例如 Slack 消息或 GitHub 通知。它们和 Slack、GitHub **插件**是分开的，可能需要单独的连接流程。

匹配规则要窄：官方例子是 `#customer-escalations` 频道里出现工单链接、且包含 “needs repro” 才动手。像「每条新消息都听」这种宽规则会产生噪音、消耗用量，也更容易在无关输入上误动作。

::: example 窄事件规则
```text
当 #customer-escalations 里的消息包含支持工单链接，并且出现 “needs repro” 时：
打开工单，在预发环境复现，把复现包发回本对话。
未经批准不要回帖到 Slack。
```
:::

定时与事件可以并存，但不要让同一条意图被两套触发器各跑一遍——先想清楚「谁是主闹钟」。

## 3. 先 Test run

新建或改完例程后用 **Test run**。测试会真正做事：会打开网站、改文件、调用已连接的工具。用安全输入，并把写入动作留在审批后面。

检查这五条再正式启用：

- 是否选到了当前数据，而不是过期缓存 
- 输出格式是否符合约定 
- 每一步是否有来源或可追溯记录 
- 是否停在了你要的审批点 
- 失败状态是否写得清楚 

手机端可以暂停或恢复例程，但编辑说明与 **Test run** 需要桌面端。

## 4. 写意图，不要冻死工具菜谱

例程说明应写：**目标、输入、验收、缺数据策略、审批边界**。不要把某次成功时的点击序列、临时 URL、会话 Cookie 步骤原文粘进例程当「永久剧本」——网站一改版就会碎。把可复用步骤沉到[技能](/workbench/skills/)，例程只负责「何时调用哪条技能」。

源系统、连接器字段或页面结构变了之后：先暂停 → 手动跑通 → 更新技能 → 再 **Test run** → 恢复启用。

## 5. 两个情报例程示例

下面提示词来自个人实践改写，来源列表用占位符，换成你自己的即可。读首页时间线需要安装并登录 X 插件；只查公开内容不用连接。完整步骤见场景[每日 AI 情报例程](/scenarios/intel-digest/)。

::: example 每日情报
```text
帮我做一个每天的 AI 动态情报：
1. 来源：X 上我的时间线和我关注的这几个博主：[博主列表]，公众号：[公众号列表]，B站：[UP主列表]
2. 时间范围：当天 0 点到现在
3. 按点赞数从高到低排序，挑最值得看的十几条
4. 每条写清楚：一句话说是什么事、大概多少赞、原文链接
5. 只是个人说法、还没被官方或其他来源证实的，在后面标「未核实」
6. 用我能直接看懂的中文写，不要堆术语
7. 以后每天早上 [时间] 自动跑一次，跑完发给我
```
:::

::: example 定时精选
```text
每天 9:07、14:07、21:07 各跑一次，整理我 X 首页时间线上和 AI 有关的内容。
每条标一个标签：新发布、新玩法、旧闻翻炒。
每条写一两句要点，附原帖链接。
最后单独列出今天最值得看的 3 条，说明为什么值得看。
和上一次整理过的内容去重，重复的不要再发。
```
:::

也可以做「只盯官方账号有无新发布」的小时级雷达：没有新动态就保持安静，有了再提醒——同样依赖窄规则，避免空转烧用量。

## 6. 管理、暂停与上限

打开 Bot 的 **View conversation details**，再进入 **Routines**，可以：启用或暂停、跑一次测试、改时间表或说明、查看最近成功与失败、删除。

**什么时候该暂停**：源系统维护、连接器掉线、你要改技能、出差无法看审批卡、怀疑误触发。暂停比删掉再建更稳；回来后先 Test run 再开。

官方上限（以文档为准）：

| 项 | 说明 |
| --- | --- |
| 每个 Bot 拥有的例程 | 最多 50 条 |
| 每条保留的运行记录 | 最近 20 次 |
| 时间表间隔 | 至少 5 分钟 |
| 删除 | 立即生效，不可撤销；删 Bot 会一并删掉它拥有的例程 |

长时间不回来时，Grok Bot 可能询问是否继续运行；没有回应就可能暂停。回来后记得检查已暂停的例程。

## 7. 为信任而设计

- 先自动化「准备」（草稿、对账、推荐），再谈自动执行。 
- 发送、购买、删除、发布、改生产系统一律审批。 
- 写明无数据 / 旧数据策略。 
- 网站、连接器或源格式变了之后重新 Test run。 

::: approval
Test run 和正式例程都会动真格。外发、付款、删库、发帖前必须停在审批卡；你不点发送，Bot 就不该发出去。
:::

## 你要检查什么

- 是否先有可复用技能，再挂例程。 
- 时间表是否落在你能盯的第一周（优先工作日白天）。 
- 事件监听是否足够窄。 
- 说明是否写意图与验收，而非冻死的点击菜谱。 
- 出差 / 改版时是否先暂停。 

## 常见坑

- 没过 Test run 就开闹钟。 
- 「每条新消息都听」烧用量还误动作。 
- 无人值守撞上过期审批卡，误以为已经发出。 
- 源系统改了却不更新技能，例程天天失败。 
- 隐藏 Bot 却忘了暂停它拥有的例程。
