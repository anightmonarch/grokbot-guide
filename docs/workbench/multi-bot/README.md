多个 Bot 的价值在于分工和交接，而不是每个都从零认识你。官方建议：当工作有独立目标、工具集、风格、审批边界或固定日程时，再拆出单独 Bot。

## 1. 什么时候该拆

值得拆的信号：

- 一类工作要长期有人负责（选题、对账、值班晨报）。  
- 审批边界不同（一个能起草，一个绝不能外发）。  
- 工具集不同（一个重度用 Notion，一个重度用 GitHub）。  
- 需要并行：搜集与撰写同时进行。  

不值得拆的信号：偶尔问一句、没有固定交付、还没跑通第一单——先在一个窄职责 Bot 里做完，再决定是否拆。

拆之前先看[Bot 馆](/bots/)里有没有接近的模板：导入后改描述与边界，往往比从零捏一个快。模板会暴露配置，分享前去掉密钥与内部地址（见[共建](/contribute/)）。

## 2. 建一个群

1. 在侧边栏选 **New**。  
2. 在 **New chat** 里选两到六个 Bot。  
3. 打开群，必要时改掉自动生成的群名。  
4. 说明共同目标和下一步由谁负责。  

手机上可用 **+ → New Group Chat**。群成员可按客户端能力调整；以你看到的菜单为准。

群里可以让 Bot 互相 `@`、互相交接。审批请求、密钥与登录请求、邮件和 Slack 草稿**不会**出现在群里——这些仍在一对一或专用流程里处理。外发类动作请回到与负责 Bot 的一对一对话，见[Channels](/workbench/channels/)。

![选 2–6 个 Bot 建群示意](/tutorial/group-chat-create.png)


## 3. 怎么说话

- 正常写，让参与的 Bot 决定谁回应。  
- 某一件事由一个队友负责时，输入 `@` 指定它。  
- 用 **Reply** 把你的回答直接送给某个 Bot。  
- `@everyone` 只在需要全群更新时用，避免刷屏与重复劳动。  

对话里也可以 `@` 例程和连接器，把「谁做、用什么工具、何时跑」写在同一条请求里。

::: example 群里的分工首句
```text
目标：本周选题包。@小夜 从收藏里挑 5 条写入 Notion「选题库」，每条附链接。
@批签 只负责检查外发边界，不要改选题内容。挑完后在群里汇总，发帖前必须停在审批卡。
```
:::

## 4. 交接

一个 Bot 可以异步给另一个 Bot 发消息，接收方醒来处理并回话，过程在对话里可见。适合：一个 Bot 掌握数据源，另一个负责交付；或需要专家复核草稿。

每个阶段只设一个负责人。并行交接太多会产生重复劳动和噪音。团队管理员可以在控制台用 **Messaging Between Bots** 关掉这项能力。

Bot 往群里交接的消息目前以文字为主——需要附件时，让负责方把文件写到 `/workspace` 约定路径，并在交接句里写清路径，而不是假设群消息能带上大文件。

## 5. 管家式组织思路

可以把一个主 Bot 当作管家（教程里带黄色标签的「总管」角色），由它统筹其他 Bot：派活、收口、问进度。专项 Bot 各自守一段（情报、写作、工程）。这不是官方强制架构，而是一种组织方式：主 Bot 负责协调，不代替所有专长。

所有 Bot 仍共用一台云电脑——管家模式**不是**安全隔离。凭证与文件边界见[云电脑](/start/computer/)与[安全与审批](/workbench/security/)。

**不要在 Bot 之间「共享密钥」当协作手段**：登录态本来就在共享电脑上互通；额外把密码写进某个 Bot 的描述或对话，只会扩大泄露面。需要隔离的工作，应在源站用不同账号 / 作用域，并在不用时退出登录。

## 6. 复制、隐藏、删除

- **Duplicate**：复制资料与例程等，不复制历史与记忆。新副本要重新认识你，见[记忆](/workbench/memory/)。  
- **Hide from sidebar**：名单变干净，但要停例程请先暂停；可从 **Hidden Bots** 再显示。  
- **Delete**：不可恢复对话与例程；共享电脑文件仍在。  

侧边栏可用 **Pin** 把常用 Bot 钉在顶部，方便在多 Bot 名单里快速切回管家或值班角色。

## 7. 并行时的电脑限制

多个 Bot 可以并行推理、调用连接器和处理文件。每个 Bot 在共享电脑上有自己的屏幕，但同一时刻一个 Bot 的屏幕上只能跑一个 computer-use 任务。设计群任务时：把「要抢屏幕的点击活」错开，或交给不同阶段的负责人，避免互相打断。

快捷键与协作细节以官方 [Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration) 为准（例如命令面板一类入口）。本页只固定群聊与交接的用法。

## 8. 推荐的最小编制

官方建议从最小有用名单起步：

1. 先给一个 Bot 端到端责任。  
2. 只有出现稳定专长职责时再加第二个。  
3. 交接本身需要可见时，再进群聊。  
4. 外发动作始终留在审批后面。  

实践里常见「管家 + 情报 + 写作 + 批签」四段，但你不必一次建满——每加一个，就写清描述、审批边界与是否允许它碰共享登录。

## 你要检查什么

- 每个 Bot 的描述是否写清职责与审批边界。  
- 群目标是否一句话能说清；是否指定了唯一负责人。  
- 外发类动作是否仍走审批，而不是在群里「口头同意」就算数。  
- 交接链是否过长（超过两跳往往该合并职责）。  
- 是否把密钥写进了某个 Bot 的描述或群消息。  

## 常见坑

- 还没跑通首单就拆五个 Bot，每个都半吊子。  
- 在群里等草稿卡 / 审批卡——它们不会出现在那里。  
- 交接链超过两跳还没人收口。  
- 用「再开一个 Bot」代替撤权或清文件。  
- 并行两个 computer-use 抢同一屏幕导致互相打断。
